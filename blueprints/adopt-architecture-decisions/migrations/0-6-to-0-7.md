# Upgrade the ADR bundle to okf-profiles v0.7.0

Move this repository's existing `docs/adr` bundle onto the v0.7.0
architecture-decision profile. The bundle already exists and already validates
against an older profile — this edge changes the pin and brings the corpus up to
the constraints that pin newly enforces. Do not re-run adoption, do not
renumber ADRs, and do not restructure the bundle.

The exit condition is that the repository's own ADR check passes under
`--strict`.

## First: establish where this repository actually is

Do not trust the `--from` version that invoked this edge. Read
`docs/adr/profile.dhall` and find the `okf-profiles` tag it pins. That tag is
the real starting point.

This edge is declared as `0.6.0 -> 0.7.0` because v0.7.0 is the only release
that changed the architecture-decision profile — v0.4.1 through v0.6.0 left it
untouched. A consumer pinned anywhere in that range is upgrading across the
same single change, and a wider window such as `--from 0.4.0 --to 0.7.0`
selects this one edge.

- Pinned tag is **anything from v0.4.0 through v0.6.0** — proceed.
- Pinned tag is **already v0.7.0** — the pin needs no change. Skip to
  *Bring the corpus up to the new constraints*; the corpus may still be
  failing.
- **No `docs/adr/profile.dhall`, or it does not pin `okf-profiles`** — this
  repository never adopted the shared profile. Stop and report that
  `seihou agent run adopt-architecture-decisions` is the correct entry point,
  not this migration.

Also check whether the descriptor has been customized. A project may have added
its own overrides on top of the imported profile. Preserve every such override;
only the pinned tag, its hash, and the presence classifications described below
are yours to change.

Run the repository's ADR check now and keep the output. You need to know which
failures you inherited, and the check command itself — often a `just`, `make`,
or `npm` target wrapping `okf validate`. If none exists, use:

```sh
okf validate docs/adr --strict --profile docs/adr/profile.dhall \
  --profile-enforce --log-enforce
```

## What v0.7.0 changes

v0.7.0 restates the ADR frontmatter as structured field rules. Two of them
change which documents pass:

**`description` and `timestamp` are promoted from recommended to required.**
Under `--strict` an absent recommended field was already an error, so a project
that ran `--strict` sees no new failure here. A project that ran without
`--strict` sees these become hard errors for the first time.

**Three fields gain formats that are now checked.** These are new enforcement,
not new fields, so a corpus that passed on v0.4.0 can fail on v0.7.0 without
having changed:

| Field | Constraint | Rejected examples |
|-------|-----------|-------------------|
| `timestamp` | RFC 3339 **UTC** — must end in `Z` | `2026-05-04T14:43:01-07:00` |
| `date` | calendar date, exactly `YYYY-MM-DD` | `2026-5-4`, `May 4 2026`, a full timestamp |
| `docId` | strict `ADR-N`, positive, no leading zero | `ADR-007`, `ADR-0`, `adr-7` |

**`supersedes` and `supersededBy` gain handle-reference rules.** Entries must be
local `ADR-N` handles or `mori:` URIs. A dangling handle pointing at an ADR that
does not exist in this bundle is now an error.

## Change the pin and the presence classifications

Set the pin to v0.7.0 and reclassify the three provenance fields as `optional`.
Both halves are required together — do not do one without the other.

`optional` is okf 0.4.0.0's third presence classification: never reported when
absent, in any validation mode, while every constraint the rule declares still
applies whenever the field *is* present. It exists for exactly this case,
lifecycle and provenance metadata whose absence is ordinary rather than
deficient.

Without the reclassification, `supersedes`, `supersededBy`, and
`originatingPlan` remain `recommended`, and under `--strict` every ADR that
lacks them fails. Essentially every real corpus lacks them: a live decision that
has never been superseded has nothing to record, and ADRs predating plan
tracking have no originating plan. Bumping the pin alone therefore turns a
green bundle red.

The blueprint ships the target descriptor as
`architecture-decisions-profile.dhall` in the reference directory. If the
project's existing descriptor has no customizations, install it as-is. If it
does, apply the same two changes by hand and keep the customizations.

Re-freeze the integrity hash after editing — the hash must match the new tag:

```sh
dhall freeze --inplace docs/adr/profile.dhall
```

Never hand-write a `sha256:` value, and never delete the hash to make an import
resolve.

## Bring the corpus up to the new constraints

Work from the validator's output, not from assumption. Re-run the check after
the pin change and fix what it reports.

**Timestamps carrying a UTC offset.** Convert to the `Z` form **preserving the
instant** — `2026-05-04T14:43:01-07:00` becomes `2026-05-04T21:43:01Z`. Do not
restamp to the current time. `timestamp` records the last meaningful revision,
and `okf log` coverage is checked against it, so restamping both destroys
history and can break the log gate.

**Malformed `date` values.** Normalize to `YYYY-MM-DD`. `date` is the original
decision date and is not interchangeable with `timestamp`; if a document has
only one of the two, derive `date` from the decision's own recorded date, never
from today.

**Missing `description` or `timestamp`.** Write a one-sentence `description`
from the decision's own content. For a missing `timestamp`, use the last commit
that meaningfully changed that file:

```sh
git log -1 --format=%cI -- docs/adr/<file>.md
```

Convert that to the `Z` form. Do not invent a timestamp, and do not use the
current time for a document you did not just write.

**Zero-padded or malformed `docId`.** `ADR-007` must become `ADR-7`. The
document ID is the enforced identity — the filename may stay zero-padded.
Changing a handle breaks incoming references, so when you change one, search the
repository for citations of the old form and update them in the same pass.

**Dangling `supersedes` / `supersededBy` handles.** Point them at a real ADR in
this bundle, or use the full `mori:` URI when the target lives in another
repository. Do not delete a supersession relationship to make validation pass —
if the target genuinely does not exist, report it rather than silently dropping
the link.

## Scope

This edge covers the architecture-decision bundle only. If the repository has
other OKF bundles — research documents, improvement requests, use cases — they
have their own profiles and are **not** in scope. Leave them alone. Mention them
in your summary if they also pin an old tag, so the user knows they remain.

## Do not

- Do not weaken the profile to make the corpus pass. Reclassifying the three
  provenance fields as `optional` is the only sanctioned relaxation; do not move
  `description`, `timestamp`, `date`, `docId`, `title`, `status`, or `type` out
  of `required`, and do not drop `--strict` from the check.
- Do not rewrite ADR prose. This edge touches frontmatter, the descriptor, and
  references to changed handles.
- Do not renumber ADRs to close gaps.
- Do not add `sources`-style fields the ADR profile does not declare.

## Before you finish

Run the repository's ADR check and confirm it passes:

```sh
okf validate docs/adr --strict --profile docs/adr/profile.dhall \
  --profile-enforce --log-enforce
```

If `log.md` exists and the check reports stale log coverage, append a dated
entry with `okf log add` describing this upgrade.

Report: the tag moved from and to, how many concepts now validate, every
document whose frontmatter you changed and which field, any `docId` change with
the citations you updated alongside it, and anything you could not resolve.
